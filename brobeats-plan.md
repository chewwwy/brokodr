# BROBEATS — plan for approval

A new section of Bro.Kodr: beatbox into a mic, hear a real kit; capture and edit samples;
build your own kit by dropping sounds onto pads; loop it all and sculpt each loop with the
existing 22 modules.

**Nothing is built yet. This is the plan. Correct what's wrong and I'll start.**

---

## What you actually asked for — it's four things

Worth separating, because they have very different risk profiles:

| # | Feature | Risk | Why |
|---|---------|------|-----|
| 1 | **Drum rack** — 16 pads, drag-and-drop samples, per-pad ADSR/pitch/choke | Low | Sample playback is solved. `file-player.js` already does WSOLA stretch + resampling. |
| 2 | **Sample capture + editor** — record from mic or import, trim/normalise/fade, send to a pad | Low | `recorder.ts` already captures takes and `processForExport()` already trims, normalises and fades. Mostly UI. |
| 3 | **Looper** — record loops, layer them, each loop gets its own module chain | Medium | Needs a clock, and needs the chain runner made reusable. Architectural work, but known. |
| 4 | **Smart Voice** — beatbox detection driving the pads | **High** | The only genuinely uncertain piece. Latency and classification accuracy decide whether it's magic or a toy. |

**Decision: build them in that order — 1, 2, 3, 4.** Each is useful on its own, and it means
the risky part lands on top of a foundation that already works rather than being the thing
everything else waits on. If Smart Voice disappoints, you still have a sampler, an editor
and a looper.

---

## The one architectural change everything depends on

Right now `Engine` (`dsp/engine.js`, 418 lines) owns the chain: an array of `Slot`s, dry/wet
per slot, bypass, ordering. That logic is exactly what a pad needs and exactly what a loop
needs — you asked for modules on loops, and per-pad sculpting is the same problem.

**Decision: extract the chain runner out of `Engine` into a reusable `Chain` class**
(`dsp/core/chain.js`). `Engine` keeps one as its master chain and behaves identically; pads
and loops each get their own. Zero behaviour change to what exists today — it's a lift, not
a rewrite — but without it, per-pad and per-loop effects mean duplicating slot logic three
times and they'd drift.

This is the first commit, done on its own, verified against `scripts/verify-dsp.mjs` (193/193)
before anything new is added.

## Phase 1 — the drum rack

### New DSP files (backend-agnostic, same rules as everything else: no allocation in `process()`, no DOM, no AudioContext)

- **`dsp/core/drum-voice.js`** — one pad's voice. Sample playback with:
  - **ADSR** — this is your "long bass and short" control. Attack/decay/sustain/release
    applied as a gain envelope over the sample. Set release short and an 808 becomes a tick;
    set it long and it booms through the next bar.
  - Pitch (semitones, reusing the resampler already in `file-player.js`)
  - Start offset / reverse
  - Gain, pan
  - **Choke groups** — pad 3 (open hat) cut instantly by pad 2 (closed hat), the way real kits work
  - Velocity → gain curve
  - Round-robin: up to 4 samples per pad, cycled, so repeated hits don't machine-gun
- **`dsp/core/drum-rack.js`** — 16 voices + a mixer. Each voice optionally runs through its
  own `Chain`, so you can put the bitcrusher on the snare only.

### The starter kit — synthesised, not sampled

**Decision: ship a default kit generated by our own DSP, not audio files.** An 808 kick is a
sine with a pitch envelope; a snare is noise plus a tuned body; a hat is bandpassed noise
with a fast decay. We already have oscillators, filters and noise.

Why this way:
- Zero licensing questions, zero megabytes to download, kit works on first launch
- It's tweakable rather than frozen — the kick's tune and decay become knobs
- It's exactly the story the rest of the app tells: hand-written, not stock

Drag-and-drop then **replaces** any pad with a real sample when you want one. You are never
stuck with the synth kit — it's just what's there before you've loaded anything.

`dsp/core/drum-synth.js` — four generators: kick, snare, hat, clap/rim.

### UI

- **`components/brobeats/pad-grid.tsx`** — 4×4 grid, same metal skin as the rack (`mk` classes,
  amber `#f0a83c`, per-category accent). Drop a file anywhere on a pad to load it. Pads light
  on trigger and show a small waveform thumbnail.
- **`components/brobeats/pad-editor.tsx`** — the selected pad's ADSR (draggable envelope
  curve on canvas, matching the EQ curve treatment), pitch, gain, pan, choke, round-robin slots.
- Triggerable by mouse, computer keyboard, and MIDI (`audio/midi.ts` already exists).

### Where samples live — BUILT AND VERIFIED

**Decision: samples are stored client-side, not in the database.** Audio is far too big for
a SQLite text column, and the presets table is a JSON-document pattern that wants to stay
small. So: **IndexedDB** on web, **real files on disk** via Electron IPC on desktop. Kits
store references, not audio.

New `kits` table follows the `presets` precedent exactly — an opaque JSON `kit` document that
tolerates schema drift, plus a `summary` column for the browser list. One new route file,
`api/routes/kits.ts`, one query file, `web/queries/kits.ts`.

**What got built:**

- `audio/sample-store.ts` — one async facade over three backends, picked once at runtime:
  real `.wav` files under `Music/Bro.Kodr/Samples` on desktop, IndexedDB on web, and an
  in-memory fallback for a locked-down browser or a Node script. `put`/`get`/`list`/
  `remove`/`prune`, all failure-tolerant: a quota error or a missing file returns null and
  the sample still reaches the pad from memory, because storage is a convenience and not a
  correctness requirement.
- `PadSource.sampleId` — a stable, opaque id (`smp_<time>_<rand>`) separate from
  `sampleName`. The name is what the user sees and renames; the id is what the audio is
  filed under. Tying storage to the name would orphan a sound on rename and collide when
  two files share one. It also means a break chopped across sixteen pads stores its audio
  once, not sixteen times.
- `decodeWav()` in `recorder.ts` — the exact inverse of the existing `encodeWav()`, so what
  the desktop build writes opens in any DAW and what any DAW writes loads here. Walks the
  RIFF chunks rather than assuming `data` at offset 44, and deliberately does **not** use
  `decodeAudioData`: restoring a kit has to work with the engine in standby, which is
  precisely when there is no AudioContext.
- Electron IPC: `fs:readBinary`, `fs:delete`, `fs:samplesDir` alongside the recorder's
  existing `fs:writeBinary`. The binary read slices to the exact view — Node pools small
  Buffers, so handing back `buf.buffer` raw would ship other files' bytes across IPC.
- `EngineClient` — writes a pad's audio to the store on drop (fire-and-forget, so a drop
  still feels instant), restores every sample pad from the store at startup, and re-pushes
  it on ENGAGE. That last part closed an older hole: a sample dropped in standby never
  reached the worklet, because there was no node to post it to.
- Clearing a pad does **not** delete its audio — the same id can be on several pads and
  inside several saved kits. `pruneSamples(keep)` is the separate, explicit sweep.
- `kits` table, `api/routes/kits.ts`, `web/queries/kits.ts` — the preset pattern exactly.
  The library is additive: the working kit still autosaves to localStorage on every change,
  and these rows are the named snapshots the user chose to keep.

**Verified:**

- `scripts/verify-sample-store.ts` — 48/48. WAV float round trip is bit-exact; 16- and
  24-bit land within a dithered LSB; stereo sums to mono without doubling the frame count;
  malformed and chunk-padded files behave; ids are unique across 500 draws and filename
  safe; put/get/list/remove/prune hold, including re-putting an id replacing rather than
  duplicating, and an unknown id reading as null instead of throwing.
- In the browser: dropped a synthetic 12000-frame buffer on pad 1, confirmed the row in
  IndexedDB (right id, name, rate and audio), then **hard-reloaded** — the pad came back
  with `frames: 12000` and its id, and firing it drove the pad meter to 0.285. Before this
  it would have come back silent with a greyed-out name.
- Kits API end to end against the live server: create → list → get → update → remove, 16
  pads stored, pad 1 carrying its `sampleId`, and the whole document 5.4 kB — references,
  not audio, exactly as intended.

### The kit library UI — BUILT AND VERIFIED

`components/brobeats/kit-browser.tsx`, a third tab in the BROBEATS right-hand column
(PAD / SAMPLE / **KITS**), mounted alongside the other two and hidden rather than
unmounted, for the same reason they are: a tab change must never throw work away, and the
list is a query that would otherwise flash "loading" every time you looked at it.

Search, favourites-only filter, and per-row favourite / rename / overwrite / delete, with
`SAVE AS…` writing the current sixteen pads under a name. Saving or renaming the active kit
renames the document too, so what the list calls a kit is what the kit calls itself.

Two deliberate differences from the preset browser:

- **A load reports its missing audio.** A kit stores `sampleId` references, not samples, so
  after loading it checks the sample store and says how many sample pads came up silent.
  Loading a kit whose samples are all present says nothing extra; loading one that came from
  another machine tells you plainly why a pad is dead instead of letting you tap it and
  wonder. Same outcome every DAW gives for missing media — the difference is being told.
- **No `.vkkit` import/export.** A kit file carrying settings but no audio is a trap, and one
  carrying audio is a different feature (a kit archive) with its own design. Until that
  exists, kits stay where their samples are.

Deleting a kit leaves its samples in the store: the same id may be on the pads right now or
inside another saved kit. `pruneSamples()` stays the separate explicit sweep, and nothing
calls it yet — it must union the live kit's ids with every stored kit's before it runs.

**Verified in the browser, through the UI rather than through `fetch`:** dropped a sample on
pad 4, saved it as a kit from the panel (row appeared with "15 synth · 1 sample"), reset the
kit to stock, clicked the row — the kit came back named, pad 4 carrying its sample, and
firing it drove the pad meter to 0.84 against 0.79 for a stock synth pad. Then **reloaded the
page cold** and did it again from an empty React tree: 0.70 on the restored pad. Favourite,
rename, search, favourites-only and delete all confirmed against the live server, and the
list emptied when the test rows were deleted. (Both zero-meter readings on the way there were
the headless AudioContext sitting suspended until a real click, not the kit path.)

## Phase 3 — the looper

- **`dsp/core/looper.js`** — N loop tracks (starting at 4), each recording post-chain audio.

UI: **`components/brobeats/loop-deck.tsx`** — track lanes with waveforms, transport, and a

**Status: built and verified — DSP core, engine wiring and the LOOPS workspace are all in.
Re-runnable smoke test: `bash scripts/verify-loops-ui.sh` (needs the web dev server up).
It covers the workspace switch, transport, record/close/overdub/undo, stop/play, per-lane

## Phase 4 — Smart Voice (the beatbox detector)

### Architecture

Not the 1024-point FFT in `spectral.js` — at 48k that's a 21 ms frame, far too coarse to
catch an onset in time. Time domain instead:

```
mic -> 3-band split (biquads we already have)
    -> fast envelope followers per band
    -> onset = spike in summed envelope derivative
    -> feature extraction at the peak
    -> nearest-centroid classifier -> pad trigger + velocity
```

- **`dsp/core/onset.js`** — detector + feature extraction. Features: band energy ratios,
  spectral centroid, zero-crossing rate, attack slope, decay estimate.
- **`dsp/core/beat-classify.js`** — nearest-centroid classifier with per-user centroids.
  No ML, no model file, runs in microseconds.

### Two-stage triggering

You cannot classify a hit from its first sample. So:

1. **Provisional fire at ~2-3 ms** — low vs high energy shows up immediately, which is
   usually enough to separate kick from hat. Sound starts early.
2. **Full decision at ~5-8 ms** — used for the harder snare/rim/clap distinctions.

**Status: built end to end and verified, mouth-to-pad.** The classifier core
(`core/onset.js`, `core/beat-classify.js`) passes 75 numeric checks
(`node --expose-gc scripts/verify-beat-classify.mjs`) against the kit's own one-shots —
both stages, gating, velocity, calibration capture, pad routing, ring wrap, and a
no-heap-growth run. The engine and worklet wiring, both backends and the client add
another 111 (`node scripts/verify-engine-voice.mjs`), and the training maths 78
(`bun scripts/verify-voice-train.ts`). The UI — `smart-voice-panel.tsx` and
`calibrate.tsx`, on a new VOICE tab in BROBEATS — passes 13 browser checks
(`bash scripts/verify-voice-ui.sh`), which drive the real detector by wiring synthetic
transients straight into the worklet node, since the sandbox has no microphone: master
switch, detector controls, class routing, live detection, a full calibration pass and its
undo, the disarm-on-look-away guard, and a restart replaying the profile.

Still owed, and only answerable on a real machine: how the flow feels with an actual
voice, and whether eight hits a class is the right ask.

Two findings from writing that test worth recording, because both were real bugs shipped
in the first draft of the file and both are the kind that would have read as "the
beatbox detector is just bad":

- **Stage 1 cannot read the block the onset fired in.** A hit starts at an arbitrary
  offset inside that block, so reading the band envelopes at its end reads an arbitrary
  fraction of the attack — the factory kick's band vector swung across a 0.43-wide range
  depending only on where in the block it landed, against a 0.17 gap between the kick and
  clap rows. Stage 1 now waits one block (2.7 ms), where that spread collapses to 0.095.
  Provisional fire is therefore ~3 ms rather than ~2, and it is right instead of a coin
  flip. Measured by `scripts/measure-attack-features.mjs`.
- **The two stages need two centroid tables.** Every drum's attack is broadband, so at
  3 ms almost everything is mid-dominated and looks nothing like the same hit at 8 ms.
  Comparing attack-time bands against window-time centroids called every kick a clap,
  confidently and early. Both tables are now measured rather than tuned by ear, at the
  point each is actually read.

Realistic total, mouth to kit: **15-35 ms** including the output buffer. At the low end that
feels tight and playable. At the high end you'll feel it, the way a bad stage monitor feels.
**I cannot promise a number until it's measured on your machine** — desktop round-trip has
never been measured here, and that's the same measurement the Android spike is waiting on.

### Calibration — the single biggest quality lever

**`components/brobeats/calibrate.tsx`** — 30 seconds: "give me eight kicks", "eight snares",
"eight hats". Sets the class centroids to *your* mouth. This is the difference between
mediocre and genuinely impressive. Every beatboxer is spectrally different and a
factory-tuned classifier will always feel slightly wrong on someone.

Calibration profiles save to the `kits` document so your profile follows your kit.

### Known limits — going in with eyes open

- Rolls above ~12 hits/sec blur; onsets merge
- Throat bass and inward clicks are spectrally strange and will misfire
- Simultaneous kick+hat (which good beatboxers do constantly) breaks single-label
  classification — needs a dedicated combo class, planned but not in the first pass
- Singing over the top false-triggers unless gated. A sensitivity/gate control is mandatory,
  not optional.

## Phase 5 — the native low-latency host (WASAPI exclusive / ASIO)

**Why this phase exists:** the `.exe` does not make the app faster. It runs the same
AudioWorklet engine as the browser, which on Windows is WASAPI *shared* mode, ~15–35 ms
round trip. That is a driver-model limit, not a code-quality one — no amount of tuning the
DSP moves it. Getting to the 3–8 ms a hardware monitoring path gives you means owning the
device from native code. That is this phase, and nothing else in the app changes.

**What is already done for it.** `native-backend.ts` is not a placeholder — it is a
complete, typed contract: `NativeBridge` (12 methods), the driver enum, the device/open/
close protocol, the command and meter shapes, and an `available === false` fallback that
explains itself. It implements `EngineBackend`, and `engine-client.ts` already probes
`isNativeAvailable()` and prefers native when true. **The UI needs zero changes.** The DSP
was also written for this from day one: pure math over `Float32Array` with an explicitly
passed sample rate, allocation-free, no `AudioContext`, no DOM, no Node. Porting is
compiling the same algorithms, not redesigning them.

### The honest split: what can be built here, and what cannot

This is the first phase where the sandbox is a real constraint, so I want it stated up
front rather than discovered at the end.

**5a — portable core. Fully buildable and testable in this Linux sandbox.**

- **`packages/native/src/ring.{h,cc}`** — the lock-free command ring the addon writes and
  the audio thread drains. Single-producer/single-consumer, the same 6-int stride the
  worklet already uses, so `OP.PARAM` … `OP.VOICECAL` (1–19) transfer unchanged.
- **The DSP port. Correcting myself:** an earlier draft of this plan said the preferred
  route was "WASM on the native audio thread, keeping the `.js` as the single source of
  truth." **That route does not exist.** Emscripten and every AOT wasm toolchain compile
  C/C++ — not JavaScript. Keeping JS canonical would mean embedding a JS engine (QuickJS,
  V8) in the audio callback, and a garbage collector in a real-time callback is exactly
  the glitch we spent four phases avoiding. So the real choice is between two routes, and
  it is a genuine architectural fork worth deciding deliberately:
  - **(b) Port to C, native only.** ~6,200 lines of DSP transliterated. The modules were
    written C-like (typed arrays, explicit state objects, no closures in hot loops)
    specifically to make this cheap, so it's mechanical rather than clever. The cost is
    that it **forks the DSP into two implementations that must stay bit-identical
    forever**, while the existing 307-check `verify-dsp.mjs` only guards the JS one.
  - **(c) Port to C, and make C canonical for both targets.** The same port, then
    `emscripten` (3.1.69, installable here) compiles that C to wasm and the **web build's
    worklet runs the wasm too**, replacing the `.js` DSP. One source of truth, permanently,
    and the fork risk is gone rather than managed. It's the larger job and it puts the
    currently-working web build on new code, so the switch only happens once `verify-dsp`
    passes against the wasm build — the existing suite becomes the parity oracle.
  - **DECIDED: route (c).** Chosen after the spike below, not before it.
  - **Amended 2026-09-15, six modules in:** route (c) stands — one C source of truth, and
    the wasm build is how the demo runs it. What's dropped is the part of (c) that treated
    *web/native bit-identity as a shipping gate*. The desktop `.exe` is the product; the
    browser build is a demo. So the `.js` is the porting reference and the divergence is
    measured, but agreement with V8 no longer blocks a module from being done. See "What
    (c) means for the remaining port" for what this changes module by module.

#### The (c) spike — done, and it came back stronger than expected

Rather than commit 6,200 lines to a route on the strength of an argument, the route was
proven on the smallest module that could disprove it: `core/biquad.js` (254 lines, zero
allocations, already covered by `verify-dsp`). Ported to `packages/native/src/dsp/biquad.c`
as pure C99, then compiled twice — `cc -O2` natively and `emcc -O2` to wasm.

Two new harnesses, both green:

- **`scripts/verify-biquad-parity.mjs`** — a 266-case battery over all 8 filter types, the
  cascade (1–4 stages, partial engagement, over-range `setActive`) and the SVF (3 modes),
  at parameter extremes that include both clamp boundaries and a Q below the floor.
  Native and wasm each dump coefficients, a double-precision per-sample run, a float32
  block run and a 64-point magnitude response; the script replays the identical battery
  through `biquad.js` and diffs. **The battery is defined only in the C producer and the
  JS reads the parameters back out of the binary stream**, so there is no case table to
  keep in sync and no way for the two halves to drift.
- **`scripts/verify-wasm-worklet.mjs`** — the constraint I was actually worried about.
  An `AudioWorkletGlobalScope` has no fetch, no filesystem, no dynamic import and no
  top-level await, so the normal emscripten glue is unusable there.

Results, measured rather than assumed:

| check | result |
| --- | --- |
| native C vs `biquad.js` | **bit-identical**, all 266 cases |
| wasm vs `biquad.js` | **bit-identical**, all 266 cases |
| native vs wasm | **bit-identical**, 266/266 |
| `magnitudeDb` (only divergence found) | 5.12e-13 dB worst case |
| glue-free wasm module | 20.8 KB, **zero imports** |
| synchronous `new WebAssembly.Module()` | works — no await needed |
| heap growth during processing | none (258 pages before and after) |

So the tolerance rework I warned about turned out to be unnecessary for this module: the
divergence is not "small", it is zero. `sin`, `cos`, `pow`, `sqrt` and `tan` agreed
bit-for-bit across V8, glibc and emscripten's libm on this battery. Only `log10`, used
solely by the display-facing `magnitudeDb`, differed at all, and at 5e-13 dB it cannot
affect a pixel.

**Two honest caveats, because that table is more flattering than the truth warrants:**

1. **MSVC is untested.** The cross-toolchain agreement above is glibc vs emscripten, both
   on Linux/x86-64. The Windows desktop build is the one target whose libm has not been
   measured, and it is the target that matters most. `verify-biquad-parity.mjs` is built
   to run there unchanged — that is the first thing the Phase 5b MSVC CI job should do.
2. **Bit-identical today is not a guarantee forever.** It is an empirical result on one
   module and one battery, not a property of IEEE-754; `sin` and `pow` are not required to
   be correctly rounded. The harness therefore asserts a **-120 dBFS tolerance** and
   *reports* the bit-identity separately, so a future toolchain that diverges slightly
   fails only if it diverges audibly.

#### Two real bugs the port has already surfaced

The port is not just a translation exercise — running the JS and the C side by side over an
edge-value battery has already found two genuine defects. Both are worth recording because
one is a bug class to keep watching for, and the other is a bug in the shipping app.

1. **The `Math.max` / `Math.min` NaN trap (bug class, in the C port, fixed).** JS
   `Math.max(x, k)` **propagates NaN**; the obvious C translation `x > k ? x : k` does not
   — a NaN `x` fails the comparison and silently yields `k`. That turns a NaN, which is
   loud and findable, into a plausible-looking number, which is neither. It was caught by
   `gainToDb(NaN)` in the utils battery and then found at five more sites in `utils.c`, two
   in `delay-line.c` and one in `biquad.c` (`bk_svf_set`'s Q floor). The fix is NaN-
   propagating `bk_max`/`bk_min` helpers in `utils.h`; **every** `Math.max`/`Math.min` in
   the remaining modules must go through them, never through a ternary. Note the mirror
   case, because it is not symmetrical: a *guard* like `if (q < 0.02) q = 0.02;` is already
   correct, since a NaN fails the test and passes through untouched.
2. **<a id="pitch-octave"></a>`PitchTracker` octave-drops at 44.1 kHz (`PITCH-OCTAVE` — a
   real bug in the shipping JS, not yet fixed).** Fed a sawtooth of period 256 samples, the
   tracker locks solidly at 48 kHz (187.5 Hz on every block, confidence ~0.71). At 44.1 kHz
   — where the correct answer is 172.27 Hz — it alternates between 172.94 Hz and 85.97 Hz,
   reporting the sub-octave on roughly two blocks in three, at *undiminished* confidence
   (~0.70), so nothing downstream can tell the difference. This is classic autocorrelation
   octave ambiguity and it is in `utils.js` today; the C port reproduces it **bit for bit**,
   which is the correct outcome for a parity port and the reason it showed up at all.
   Consequence: Smart Voice pitch tracking is unreliable at 44.1 kHz, which is a plausible
   rate for the user's interface. Fixing it (octave-continuity constraint, or peak-picking
   against the sub-harmonic sum rather than the raw autocorrelation maximum) is a
   **behaviour change, so it is deliberately out of scope for the port** — it must land in
   both implementations at once, with the parity battery updated in the same commit, or the
   two engines will drift. Tracked as its own item, not folded into Phase 5.

Every harness is validated by mutation rather than trusted for passing — `biquad` with
three deliberate breakages, `delay-line` with six, `fft` with eight. The `biquad` three,
each caught with the correct signature: shifting the Q floor from 0.02 to
0.0201 (coefficients, magnitude and output all fail); routing the recursion state through
`float32` (coefficients stay clean, output fails at -65 dBFS — which is the empirical
proof of the "state stays `double`" rule in `biquad.h`); and perturbing `biquad.js` itself
(both C builds fail against the JS while still agreeing with each other, confirming the
three-way comparison is real and not self-referential).

The `fft` port's mutation run then found a third defect — this one in the **harness**, which
is worse than one in a module, because a blind harness makes every later module's green
result meaningless. Both halves are fixed:

3. **A crashing producer was invisible, and sub-tolerance drift was unasserted (bugs in the
   harness, fixed).** Mutating `fft.c`'s level count off by one makes the bit-reversal table
   emit indices up to `2 * size`, so the transform writes off the end of its buffers: the
   native producer took `SIGSEGV` and `buildAndRun`'s bare `execFileSync` threw an uncaught
   exception, which surfaced as a Node stack trace rather than a failed check. Separately,
   perturbing `hannWindow`'s coefficient in `fft.js` to `0.5000001` moved the output by
   1.19e-7 — under the -120 dBFS bar — and passed every tolerance check while bit-identity
   quietly fell from 221/221 to 211/221, because that count was **printed and never
   asserted**. Three fixes: `buildAndRun` now reports a dead producer as a named failing
   check and aborts with the running count instead of throwing; `compareToJs` and
   `compareToolchains` take an `expectIdentical` baseline and fail when identity regresses,
   naming the first records that drifted; and `bk_fft_init` refuses to initialise when
   `(1 << levels) != size`, so a bad level count can never walk off a buffer in the real
   host either. With those in, all eight `fft` mutants are caught with a clean diagnosis.
   **Note the tension with the libm caveat below**: a baseline drop is not automatically a
   bug, it is always something to read before re-baselining, and the reason must go in the
   commit. Baselines pinned today: `utils` 84/85/96, `delay-line` 265/267/267, `fft`
   221/221/221 (native-vs-JS / wasm-vs-JS / native-vs-wasm), `chain` 21/21/21,
   `drum-voice` 39/42/40 of 43, `drum-rack` 49/51/49 of 51. `drum-synth` pins **no**
   identity baseline by design (see its writeup): its native-vs-wasm agreement, 128/129
   records and 89/90 render fingerprints, is printed as a canary and cannot fail the run.

4. **The chain cannot recognise its own quality param (design defect in the port, fixed).**
   `chain.js` recalculates the chain's latency when a `setParam` key equals the string
   `"quality"`, oversampling quality being what moves a module's reported latency. The C
   port takes a numeric key — the point of `Slot.paramNames`, which resolves names to
   indices off the audio thread — and reserved index 0 for it as `BK_PARAM_QUALITY`. That
   is wrong by construction: the key on the wire is the param's index *within its own
   effect type's* list, so `quality` sits at a different index per type (index 5 on
   `pitch`, absent from the other 21), and a reserved constant recalculates on whatever
   param happens to sit at that index — for most effects, their first. Review caught it
   before any effect module was ported against it. The chain now interprets no keys at
   all: `bk_chain_set_param` forwards and returns, and the host calls
   `bk_chain_recalc_latency()` after a quality change, keying off the name it already has
   — which is what `worklet-processor.js` already does on the live path. The quirk that the
   JS's recalc sits *outside* its `if (slot)` guard, so a quality change aimed at an absent
   slot still recalculates, survives for free on a name-keyed host.

   The drift this invites between `param-schema.ts` and 22 `set_param` switches is closed
   by codegen, not by a checking script — a check only reports drift after someone writes
   it. `scripts/gen-param-keys.mjs` runs under Bun so it can import the schema and read the
   real `EFFECTS` export, and emits
   `packages/native/include/brokodr/dsp/param-keys.h`: an enum per effect type plus a
   `BK_P_<TYPE>_QUALITY_KEY` (or `BK_PARAM_NONE`). The header is committed so C compiles
   without a JS toolchain; `--check` fails CI when it is stale. First consumer is the drum
   port, which is where `--check` should be wired in.

The `chain` battery is the first where the *harness's own expectations* were the main
source of red, and worth recording as a pattern: seven checks failed against a correct
port because the check was wrong — a multi-block payload read as one contiguous L-then-R
run, two miscounted latency totals, an assertion that a 25 ms one-pole "reaches its
target" (it never does), and a runaway-gain bound of 8 that a legitimate 3-deep cascade at
1.25 exceeds. Mutation then found two real holes: a slot fed a **null** carrier bus looked
identical to one never given a bus at all, since only the stored pointer was observed
(fixed by counting `setCarrierBus` calls on both sides), and the recalc-on-a-miss check was
vacuous because the latency total was already correct before the miss (fixed by making it
deliberately stale first). Three first-draft mutants also escaped as *equivalent* mutants
rather than as holes — two wrote to slots the length change immediately puts out of reach,
one returned early from the hit path and so still fell through to the recalc it meant to
remove. Reading an escape is as much work as reading a failure.

`drum-voice` is the first module with libm in the audio path — `cos`/`sin` for the pan
law, `exp` for the envelope coefficients, `pow` for the pitch ratio — and so the first
where full bit-identity is not the expected result. 39 of 43 scripts match the JS bit for
bit natively, 42 under emcc, 40 across the two toolchains; the four that do not are the
`exp`-driven release case and the three that park the pan at 0.4, and they are pinned
per-case with the reason next to the number rather than absorbed into a tolerance. This is
the shape every later module with a transcendental in it will have, and the baseline is
what makes a *new* divergence visible against it.

Its mutation run is also the largest so far, and the most instructive: 94 mutants, 11 of
which escaped the first battery. Nine were genuine holes, every one of them an edge the
36-script battery simply never visited — a NaN arriving as `y0` of the linear pair rather
than anywhere else, a sub-frame attack whose increment needs flooring to 1, a `setBuffer`
index past the last layer, `release()` called on a voice already idle, a layer holding a
live pointer and zero frames, a choke fade that lands on exactly 0.0, a sustain knob
dropped under a note already holding, and the two exclusive-vs-inclusive `>= 0.5` param
thresholds. Seven new scripts and two extended ones close all nine. The other two escapes
were equivalent mutants and are documented as such **in `drum-voice.c` itself**, next to
the code that makes them equivalent, so the next reader does not re-derive the argument:
the attack-zero ternary is floored to the same answer either way, and the outer
out-of-range band is a cheap gate in front of the cubic branch's own bound, which is the
guard that actually holds. Both were replaced in the mutation set with non-equivalent
mutants on the same expressions, which are caught.

And the `chain` lesson repeated exactly: two of the nine new checks were wrong about a
correct port. Both were about when the pan smoother runs, which turns out to be worth
stating plainly — a voice that ends mid-block advances its smoothers only for the frames
it actually rendered, while a block that finds the voice already inactive runs them for
its whole length on purpose, so the next hit starts settled. The standstill across the
ending block is the only observable difference between `env <= 0` and `env < 0` in the
choke fade, because the extra frame a `< 0` test admits carries env 0 and is silent.

`drum-rack` is the first module that is almost entirely *routing* — sixteen voices, sixteen
optional chains, a solo, a mute, a gain and a flash counter — and the battery reflects
that: 51 scripted cases, 224 asserted checks, 123 mutants, all caught. The DSP in it is
two lines (the meter and the gain pass); everything else that can break is a pad index, an
ordering, or a branch that should have been skipped. That changes what a parity harness is
for. Bit-identity is near-total — 49 of 51 cases natively, 51 of 51 under emcc, 49 of 51
across the two toolchains — and the two that drift are inherited, not new: `pad-params`
and `soak` both move a pan knob, which lands in `drum-voice`'s `cos`, and glibc's `cos`
disagrees with musl's in the last bit while musl's agrees with V8's. The same shape as
`drum-voice`'s four, from the same call.

Four harness bugs are worth recording, because three of them are the same bug in different
clothes: **a test that passes while testing nothing.**

  - `S_PAD_PARAMS` had a script row written five doubles wide instead of six. `OPS`
    divides by six with integer division, so it compiled, silently dropped the script's
    last op, and shifted every op after the typo one column left. The parity diff could
    not see it — C and JS mis-read the same malformed script identically and agreed. Row
    width is now a compile-time assertion (`ROWS_OK`, the `BUILD_BUG_ON_ZERO` trick: a
    malformed script asks for a `char[-1]` and no compiler will take it).
  - `S_CHOKE_IDLE` triggered pad 3 *before* pad 2, so pad 3 was still sounding when pad 2
    fired. That is `S_CHOKE` again; the idle guard it was written for was never reached.
  - `S_RELEASE` released pad 0 while pad 0 was the only pad sounding, so a `release()` that
    ignored its index argument and always reached pad 0 passed it. It now releases pad 1
    too, with pad 0 still ringing, which is the only arrangement that can tell the two
    apart.
  - Case-relative indexing (`offsetOf`/`snapOf`/`stateOf`) now throws a named error when a
    check asks for snapshot 9 of a script that has eight, rather than reading `undefined`
    and comparing it to nothing.

Mutation found one real divergence in the port's *behaviour*, and it is a good one: **solo
cutting an idle pad destroys a pan move it has not rendered yet.** `bk_drum_voice_set_param`
on `PAN` sets the smoother's *target*; the value only walks toward it while the voice
renders. The rack never renders an idle pad. So an idle pad can sit with `value != target`
indefinitely — and `bk_drum_voice_reset` parks the smoother at `value`, discarding the
target. The rack's solo branch resets only pads that are `active`, which is what keeps the
pending pan intact; a mutant dropping that guard is therefore *not* equivalent, and no
scripted case had ever visited the combination. `S_SOLO_IDLE_PAN` now does, and proves it
by the only observable that exists: the idle pad's first hit after the solo has to land
hard left, where its target said, not centre, where a destructive reset would have left it.

Five more cases close the mechanical escapes, and each exists because the mutant that
survived named exactly what was missing — a flash length at 8050 Hz where 90 ms is 724.5
frames and `Math.round`, truncation and `rint` all give different answers; triggers and
releases at 99, −1 and 16 with the flags read before any reset could hide them; pad 15,
which nothing had ever touched, through `chainFor`/`trigger`/`reset`/`flash`; a pad left
"active with its sample yanked" and re-triggered, which isolates the choke-self question
via `trigger()`'s early return; and a `1e30` sample at +12 dB, which is the only stimulus
where the bus-level `sanitize()` does anything the voice-level one has not already done.

Three mutants escaped as **provably** equivalent — not argued, proved — and were replaced
rather than accepted:

  - Dropping `&& rk->pads[i].active` from the choke loop does nothing, because
    `bk_drum_voice_choke` is itself `if (v->active) v->choking = 1;`. The rack's guard is
    redundant with its callee's. Replaced with a mutant that writes `choking` directly and
    skips the callee, which an idle same-group pad can see.
  - Adding a bound check inside `trigger()`'s `if (!v)` branch is unreachable code:
    `bk_drum_rack_pad` returns NULL *exactly* when the index is out of range. Replaced with
    one that clamps a bad index onto pad 0 instead of rejecting it.
  - Removing the `continue` from the solo-cut branch changes nothing, because the branch has
    just reset the voice, so `active` is 0 without exception and the fall-through lands in
    the idle guard, which clears the same meter and continues anyway. That `continue` is
    defensive, not load-bearing. Replaced with one that loses the reset along with it, so
    the cut pad renders into the bus.

#### `drum-synth` — the first module shipped without a bit-identity gate

481 lines of C, six renderers, 90 render cases, **1748 asserted checks green, 155/155
mutants caught**. It is the first module done under the 2026-09-15 decision (commit
`f1da024`): the desktop build is the product, so V8 agreement is a porting aid and a free
canary, not a ship gate. Nothing about the port was loosened to get there — the gate was
never achievable on this module, for the two structural reasons written into the battery's
header and repeated below.

The battery is built in four layers, and **only the first is a hard gate against the JS**:

  1. **Integer structure, exact.** The kind table and its order, all six default param
     sets, all sixteen factory layout entries with their pad names and choke groups. No
     libm anywhere in their derivation, so there is nothing to be tolerant about.
  2. **Audio, held to bands.** Fourteen features computed by an identical no-libm ruler on
     both sides.
  3. **Invariants on the C output alone.** No non-finite sample ever, the 2 ms fade
     reaches exact zero, both arms of the peak-normalisation branch are entered, and two
     renders of identical input into differently-prefilled buffers agree bit for bit.
  4. **Native vs wasm, measured and printed, not gated.**

Layer 1 is what makes layer 2 safe to loosen, and that is the load-bearing part of the
design: param resolution is gated to exact equality, and the render cases are then driven
from the params *the C itself resolved and emitted*. A param-resolution bug therefore
cannot hide inside an audio tolerance — it has to surface in layer 1 as an exact
mismatch.

**What the divergence actually measured, which is the useful surprise.** Eleven of the
twelve compared features came back at a worst deviation of exactly **0.000e+0** against
V8 — peak, rms, t90, hf, zc, clips, first, last, frames, fade, nonfinite. The whole
observed disagreement across 90 renders is one feature on one case: `rim-tone-one.mean`,
off by **5.254e-21 absolute / 4.596e-14 relative**, which is about one float32 ULP landing
deep in a fade tail on a feature that is near zero because every kind renders essentially
DC-free. Cross-toolchain, the same story from the same call: **128/129 records
bit-identical, 89/90 render cases byte-identical by fingerprint**, the one exception being
that same `rim-tone-one`. So the module that could not be gated on bit-identity is, in
practice, very nearly bit-identical anyway — and the two reasons it cannot be gated are
still exactly right:

  - **Peak normalisation is global.** `bk_drum_render` scans the finished render for its
    peak and scales the whole buffer by `0.89/peak`. One ULP landing on whichever sample
    happens to *be* the peak rescales every other sample. A local error becomes a global
    one.
  - **The hat renderer puts a comparator on a transcendental.** `m += sin(ph[k]) >= 0 ? 1
    : -1`, six inharmonic partials as square waves, ~260k comparisons in a 900 ms ride.
    One ULP near a crossing flips a term by a full ±1.

Neither fired on this battery's inputs. Both remain certainties over a kit editor's worth
of knob positions, which is the difference between "measured clean today" and "safe to
assert forever" — precisely the distinction commit `f1da024` was about.

The bands were set from the measured spread with headroom, not guessed: float32 features
get `rel 2e-7` (just above the 1.2e-7 that one ULP costs, the tightest they can be without
being a bit-identity gate in disguise); `mean` gets `rel 1e-6 / abs 1e-15`, six and eight
orders above its worst observed; `zc` and `clips` sit on comparators where the quantum of
legitimate disagreement is a whole unit, so they get `abs 2` against counts in the
hundreds to thousands; `t90` is quantised to `1/frames`, so its tolerance is two frames'
worth computed per case rather than a constant; `frames`, `fade`, `nonfinite` and `last`
are exact.

**Nine of the 90 cases are C-only, structurally and not by excuse.** `drum-synth.js`
always allocates its scratch at the full `ceil(sr * 4)`, so the renderers' own
`Math.min(out.length, ...)` truncation branch is unreachable from the JS public API at
all. The C port takes a caller-owned buffer and can reach it, so four `trunc-*` cases do.
The rest need a sample rate the JS cannot survive on top of that: `tiny-peak` at 240 MHz,
`peak-guarded` and `peak-normalised` at 420 MHz to sit either side of the `peak <= 1e-6`
branch (rates at which the JS would try to allocate multi-gigabyte scratch), and
`hat-phase-underflow` at 1e51. `kick-wrap-boundary` is C-only for a plainer reason: it
needs a buffer shorter than four seconds. All nine are identified structurally by
`out_len < ceil(sr*4)`, held to layer 3 only, each with a dedicated invariant.

**Mutation testing took five rounds and produced two genuinely new techniques.** Five
mutants survived the battery as first written. None was a bug in the port —
`drum-synth.c` has not been edited once since it was written, across any session — and
none was accepted as an escape. Two were closed by finding an input that distinguishes
them, and three by proving the mutant equivalent and replacing it with one that attacks
the same code somewhere it is observable.

The technique worth keeping: **push sample rate and tune to values that are finite and
legal but never occur in ordinary use.** Both new cases came out of it.

  - `hat-comparator` — surviving because nothing pinned `sin`'s comparator to its
    boundary. Closed with `hat-phase-underflow`: at `tune=1e40` the hat's `base_f`
    saturates at 2520 Hz, and at `sr=1e51` all six phase increments (3.17e-47 to
    1.30e-46) fall below `2^-150` and round to exactly `+0.0` in float32. The phase array
    stays parked at `+0.0`, `sin(+0.0)` sits exactly on the `>= 0` boundary, and the
    invariant asserts every sample is positive — the `+1` arm — which a `> 0` mutant
    cannot produce.
  - `kick-wrap` — surviving because no case ever landed the kick's phase accumulator *on*
    its wrap threshold. Closed with `kick-wrap-boundary` at `sr=20, tune=20, drop=0`,
    where `f` is constant at 20 and the increment is exactly `2*pi*20/20`, landing the
    accumulator on the double nearest `2*pi`. The pristine `>` guard does not fire, so
    `sin` returns the small negative residual — a 27-frame ramp peaking at 2.449e-16 —
    while a mutant that wraps at `BK_PI` renders a buffer of **pure silence**. This one
    needed no mutant-table edit at all: the original mutant is now caught as written.

Three equivalence proofs, each replaced rather than accepted:

  - **`hat-phase-double`.** Widening the `ph[6]` declaration from `float` to `double`
    changes nothing, because every write to `ph[k]` already passes through an explicit
    `(float)` cast. Float32-ness is enforced **twice**, so a single-site mutation of
    either site alone is provably a no-op. Verified empirically as well as by reading:
    zero output difference at normal *and* underflow rates. Replaced with
    `hat-phase-f32`, a two-site mutant that widens the declaration **and** removes both
    casts — which fails 45 checks.
  - **`hat-wrap`.** Weakening the hat's wrap guard from `>` to `>=` is unobservable
    because `ph[k]` can never equal `BK_TWO_PI` exactly. `BK_TWO_PI` as a double is
    `401921fb54442d18`, whose low 29 mantissa bits are nonzero; every float32 widened to
    double has exactly 29 trailing zero mantissa bits; so no float32-derived value can hit
    it. The two neighbouring float32s straddle it (6.2831850051879883 <
    `BK_TWO_PI` < 6.2831854820251465), and `+inf`, `-inf` and `NaN` all take the same
    branch under both comparators. Replaced with `hat-no-wrap`, which deletes the guard
    entirely — 54 failed checks.
  - **`kick-hp-freq`.** Changing the kick highpass's corner from 18 Hz to 19 Hz is
    unobservable at *every* sample rate, not just the tabled ones, because `bk_clamp` is
    `x < lo ? lo : (x > hi ? hi : x)` — it tests the low bound first and returns without
    consulting `hi`, and both 18 and 19 are below the 20 Hz floor, so both collapse to
    exactly 20.0. Replaced with `kick-hp-above-floor`, 18 → 30, above the floor, where the
    clamp passes the value through and the filter genuinely differs.

Two process notes, both earned the hard way:

  - **Every fix was confirmed by swapping the real `drum-synth.c`, running the full
    battery, and then `diff -q`-ing the restore** — not by a scratch copy. A scratch
    program proves a mechanism; only the real source proves the harness catches it.
  - **A background sweep can deadlock with zero CPU and look identical to "still
    running".** The per-mutant guard inside the harness is a 120 s `SIGKILL` timeout; the
    sweep as a whole has none, so it runs under `tmux` and is polled with `ps -ef
    --forest` plus log growth. That timeout also produced the one false alarm worth
    recording: a full sweep reported `154/155 caught, 1 harness problem —
    def-snare-snap: timed out`, which was CPU contention, not an escape. Re-run in
    isolation it was caught, and a clean re-sweep came back **155/155, 0 escaped, 0
    harness problems**. A timeout is not a result; re-run it before believing it.

#### `onset` — the module that got its identity gate back

470 lines of C against a 271-line header, 43 detection cases, **54 asserted checks green,
166/166 mutants caught**. It is the second module ported after commit `f1da024` retired JS
parity as a ship gate — and it is the one that made the gate again anyway, on its own
merits rather than by policy.

**The result worth leading with: `onset` is bit-identical to the JavaScript, everywhere it
was measured.** 43/43 detection cases agree on count, on every frame position, on every
strength and on every feature at a worst deviation of exactly **0.000e+0**. All **8127**
raw detector fields — every accumulator, every follower state, every filter coefficient,
the whole lag history and the commit ring's contents — match V8 bit for bit. Cross-toolchain
the same: **397/397 records identical between glibc/x86-64 and emscripten/wasm**, worst
deviation `0.000e+0`. Under `f1da024` that identity is a canary and not a requirement, so
it is asserted as a **pinned baseline** (`43/43, baseline 43`) rather than as a
loosenable tolerance: it can only be changed deliberately, never eroded by accident.

Why this module could hold the line that `drum-synth` structurally could not: onset has no
global normalisation step and no comparator sitting on a transcendental. Its one
comparator-on-arithmetic is the zero-crossing counter, and that runs on raw sample signs,
not on `sin`. Everything else is biquads and envelope followers in `double`, which both
toolchains compute identically.

The battery is six layers, five of them hard gates:

  1. **Exact structure.** Defaults, `FEATURE_COUNT`, the ToInt32 table, lag-history sizing
     across 18 sample rates, the 38 parameter clamps, crossover coefficients, and a late
     `setParam` landing on the constructor's exact coefficients.
  2. **Detection against the JavaScript**, bit-identical and baselined.
     - **2e — the capacity bound the JS does not have.** The C `detect()` writes into a
       caller-owned buffer with a `capacity`; the JS returns an array and cannot truncate.
       Six cases find more hits than their capacity, the deepest carrying 24 committed
       measurements against 4 slots, and the assertions cover both that the hits which fit
       are the JS's and that the rest of the buffer is untouched.
     - **2b — the streaming API, block by block.** Per-block counts, `pendingFeature`,
       `commitCount`, drained features, and the live block-local `features` array at full
       width (not just up to `count`, which was one of the harness holes found below).
     - **2c — the commit ring's staleness boundaries**, 344 boundary probes, with one case
       deliberately overflowing the ring.
     - **2d — every field, raw, either side of `reset()`.** Asserts that `reset()` leaves
       a detector exactly as a fresh one, that the JS's `reset()` does too, and — the
       non-vacuity half, which is the part that actually earns the check — that all 24
       resettable fields and 46191 lag slots were dirty in at least one case first.
  3. **Invariants on the C alone.** No non-finite anywhere in 397 records, band features
     normalised or zero, features and strengths in `[0, 1]`, hits strictly ordered and
     never closer than the refractory period, non-finite input not silencing the detector,
     and silence producing no hits.
  4. **Native vs wasm**, printed and — with one deliberate exception below — informational.

**The most valuable thing this port produced is a hard gate that did not exist in any
earlier module: native held directly to wasm.** The first clean sweep read `126/170
caught, 44 escaped`, and two of those escapes, `to-int32-nowrap` and
`to-int32-nonfinite`, were contradictory — a standalone probe showed `to-int32-nowrap`
visibly changing wasm output on 13 of the 46 tabled inputs, while the sweep insisted it
escaped. Reading the assertion explained it: the to-int32 layer compared native against
the **JS oracle** only, and never native against wasm. Converting a double that is
negative or out of int32 range is undefined behaviour in C, and the two toolchains resolve
it differently — **x86-64 wraps, wasm saturates to 0** — so the single most
toolchain-divergent function in the module had no cross-toolchain assertion at all. A
53rd check became a 54th: `ToInt32 identical native vs wasm on all 46 inputs`, hard-gated,
skipped with a logged message only when `emcc` is absent. That is the first place in the
port where wasm can fail a build rather than merely be reported, and it is there because
it is the one function whose correctness is a property of the *pair* of toolchains rather
than of either one against the JS.

**Forty-four escapes, and not one of them was a bug in the port.** `onset.c` was never
edited for behaviour across the whole triage — the only edits it took were four explanatory
comments. The 44 split into real harness holes (fixed by extending the battery, which grew
it from 34 checks to 54) and equivalent mutants (replaced, never accepted). The holes worth
naming:

  - **The block-local API was never read.** `d->features` (8×4 — what live Smart Voice
     actually eats) and `d->count` were emitted by nobody. Four escapes died to snapshotting
     them after every block.
  - **Features were only compared over the hits that were found.** The verifier looped to
     `min(cCount, MAX_HITS)`, so every features row past the hit count was emitted and never
     read, and the `memset` that clears them was unobservable. One-line fix, loop to
     `MAX_HITS`; the padding it needs was already there.
  - **`reset()`/init state was only observed through audio**, which killed twelve
     `reset-*` mutants plus two init mutants once a raw field dump went in.
  - **Params were never set after init**, so the guarded refresh path had no coverage.
  - **`res->capacity` truncation was never exercised** — hence layer 2e existing at all.

**One equivalence claim from the earlier triage was refuted by measurement, and that is
the process note worth keeping.** `commit-total-eps` had been written off as unreachable:
`total` never gets small enough for the `<= 1e-12` branch to matter. Over the then-40 cases
and 628 commits the smallest `total` was 2.05e-4, which is exactly why it escaped — but a
grid search over admissible parameters found `total <= 1e-12` in 26 of 1980 trials, down to
**1.11e-14**, and never exactly zero. The branch is reachable; the claim was wrong. The
mechanism is that a **one-frame** feature window — `featureMs` 3 at a sample rate under
~667, where `ToInt32(3 * 0.001 * sr)` is 0 and the `max(1, ...)` clamp takes over — can land
on a single frame where all three band filters sit near a zero crossing. One new case
(`sr=333`, hat stimulus, amp `2^-15`) kills three mutants at once: commit 2 at 1.38e-13
falls in the `<= 1e-12` branch, commit 1 at 3.10e-12 falls in `(1e-12, 1e-6]`, and every
window in it is `ToInt32(0.999) = 0` clamped up to 1, which also pins `proc-window-min`.
A reachability argument that has not been searched against is a hypothesis.

**`detect-tail-len` got the same treatment and survived it.** The claim was that the
`+ block_size` term on `tail_frames` is slack another mutant covers. A standalone probe
linked the real pristine `onset.c` against a hand-mutated copy and swept sample rates,
feature windows, buffer lengths, block sizes and how many frames before the buffer end the
final click sits: **360 lines of disagreeing output**. At `sr=100, featureMs=3, n=256,
blk=1` the pristine build reports real features for the last hit and the mutant reports
`0,0,0,0`. Not equivalent. It is now covered by a new case, `tail-tiny-window` at `sr=250`
with a 4092 ms window, chosen so `ToInt32(featureMs * 0.001 * sr)` is 0 and the tail is
*purely* the `+ block_size` term.

**Nine mutants replaced, three removed with a proof, two folded into one.** Every
replacement was verified caught by a targeted re-sweep before being kept:

  - `refresh-q-span-floor` — a `0.001` floor on the Q-span denominator is unreachable
    because the crossover clamps guarantee a span of at least 500. Replaced with a `600.0`
    floor, above the reachable minimum, which is observable.
  - `set-unknown-key` — turning the early `return` into a `break` that falls into the
    refresh is invisible, because a refresh on an unknown key does not disturb the biquad
    cache. Replaced with one that writes `d->sensitivity = value` on an unknown key:
    direct, observable state corruption.
  - `commit-idx-cap` — loosening `idx >= MAX_HITS` is unreachable (`pending_index` is
    either `count < 8` or `-1`). Replaced with `idx >= BK_ONSET_MAX_HITS - 1`, which
    *tightens* the bound by one and drops the eighth hit's features.
  - `commit-clears-window` — dropping the `window_left = 0` clear is unobservable because
    the only reachable call site re-arms it immediately. Replaced with one that sets
    `window_left = 1`, leaving the window open so it re-commits.
  - `commit-zcr-guard` — `secs > 0.0` → `>= 0.0` is unreachable since `acc_frames >= 1` at
    every commit. Replaced with `secs > 0.01`, a materially different threshold that throws
    away short windows' ZCR.
  - `proc-ratio-lo-guard` — replaced `p_lo >= 0.0` with `p_lo > 1e-3`, moving the epsilon
    up into signal level.
  - `proc-ratio-lo-inf` → **`proc-ratio-sat`**, and this one is the instructive failure.
    The replacement was first written as a single-band change (`r_lo`'s saturation constant
    99 → 4) and it **escaped on its own targeted sweep**. The ratio is a `max` across three
    bands, so any one band's saturation constant is masked by the other two. Changing all
    three simultaneously is caught.
  - `drain-commit-guard` — the dropped condition is genuinely redundant with
    `bk_onset_read_committed`'s own first line, which returns 0 on `n >= commit_count`, and
    the callee takes a `const bk_onset *`. Replaced with an off-by-one on the bound
    (`(long long)(*drained) + 1 < d->commit_count`) that strands the newest commit.
  - `detect-final-drain` + `detect-tail-drain` — each was individually redundant with the
    other catching the observable case. Folded into a single **`detect-late-drain`** that
    removes both drains together: a window closing during the tail must still get its
    features drained.
  - `set-guard-gone`, `detect-blk-default`, `detect-count-init` — **removed**, each with a
    reachability proof written into `onset.c` as a permanent comment rather than left as a
    bare claim. `set-guard-gone`: `bk_biquad_init` resets `type`/`freq`/`q`/`gain_db` to
    the sentinels `-1`/`-1.0`/`-1.0`/`-1.0`, so any refresh cached before
    `bk_onset_init` runs cannot survive construction. `detect-blk-default`: only the
    *positivity* of the default is observable, and the `blk-1`/`blk-64`/`blk-128`/`blk-1024`
    cases already pin detection as block-size-invariant. `detect-count-init`: `res->count = 0`
    before the `memset` is a dead store, overwritten unconditionally at the function's
    single exit.

The standing rule held throughout, and it is the rule that made this module's triage
useful: **nothing goes into `onset.c`'s permanent comments unless it is backed either by a
reachability proof or by a replacement mutant the battery demonstrably catches.** Preferring
"find a differently-shaped mutant that is caught" over "prove the original equivalent"
turned two of the 44 escapes into refuted claims and one into a genuine missing hard gate.
An equivalence claim is the cheapest possible way to close an escape, which is exactly why
it deserves the most suspicion.

Two caveats carry forward unchanged: **MSVC remains completely unmeasured** — the
cross-toolchain agreement here is glibc versus emscripten on Linux/x86-64 only — and
**bit-identity is empirical per module, not a guarantee.** `onset` making the gate says
nothing about `beat-classify` or `looper` making it.

#### `beat-classify` — the two-stage classifier, and the escapes that were contracts

578 lines of C against a 362-line header, a 1703-line producer and a 1583-line verifier.
**100 Smart Voice cases, 72 asserted checks green, 107/107 mutants caught.** It is the
third module ported after `f1da024` retired JS parity as a ship gate, and like `onset` it
made the gate anyway.

**`beat-classify` is bit-identical to the JavaScript, everywhere it was measured.** All
five behavioural and structural layers report **100/100 records bit-identical to the JS**,
every one of the 17 layer-1 exact checks is bit-identical on its own records, **1002/1002
records are identical between glibc/x86-64 and emscripten/wasm**, all 100 passes agree on
every fire's block, pad, class and stage, and the worst float deviation anywhere in the
battery is exactly **0.000e+0**. Under `f1da024` that is a canary, not a requirement, so
it is printed rather than gated — but nothing in the module has ever been observed to move
off it.

Why a module with a *comparator on a transcendental* could still hold the line: Smart
Voice's only transcendentals are `20*log10()` in `gainToDb` and the `sqrt()` in classify's
confidence ratio, and neither one sits upstream of a discrete decision that the harness
can see diverge. The ratio comparison `scratch_ratio < margin` does read a `sqrt`, but
both toolchains and V8 agree on it to the last bit on every vector in the roster, and the
roster deliberately includes ties at ratio exactly 1.

The battery is five layers, four of them hard gates:

  1. **Exact structure** — 17 checks, all bit-identical. Defaults, the factory centroid and
     attack profiles with their class pads, `STAGE1_DELAY_BLOCKS`, lag-history sizing
     forwarded to the detector across 8 sample rates, all 76 parameter clamps read back
     through *both* construction paths, `init(opts) == init(NULL) + setParam` for every
     in-band key, the three ToInt32 setters over 62-record sweeps each (`setCentroid`,
     `setAttackCentroid`, `setClassPad`) plus `setCapture` over 31, `resetCentroids`,
     `classify` over 36 vectors on three different profiles (factory, poked, collapsed),
     `velocityFrom` across the floorDb × velMin × velDb grid, and hazard 1 pinned directly
     at the composed call site.
  2. **Whole passes against the JavaScript**, with hazard 3 (`every fired class inside
     [0, CLASS_COUNT)`), hazard 2 (`the wrap cases really do wrap the pending id through
     zero`), a non-finite scrub over every meter, velocity and confidence, and a
     poisoned-block row asserted to keep firing identically to its clean twin.
  3. **The stream, block by block** — the pending table at full width, caught mid-countdown
     so a slot with `pend_wait` still ticking is observed and not just its result.
  4. **The capture ring and its staleness boundaries** — 64 slots at stride 9, with rows
     that fill it, a row that overruns it, and `clearCaptures` asserted to make every probe
     stale at once *while leaving the contents in the array*.
  5. **Raw state either side of `reset()` and `resetDetector()`** — all 31 named scalar
     fields plus the ids, split into what the calls must clear and what they must
     deliberately leave alone (the profile, the capture ring, five stale pending fields),
     with the non-vacuity half asserting 32 tracked fields were dirty first and that at
     least one case leaves a used slot mid-flight.

Each of layers 2, 3 and 4 replays the same case roster independently, and the roster is
pinned once from the pass layer and compared against — so a layer that silently drops or
duplicates a case reads as a failure rather than as a smaller, still-green battery. The
`ToInt32` setters keep `onset`'s hard cross-toolchain gate: **identical native vs wasm on
all 217 records**, since converting an out-of-range double is undefined behaviour that
x86-64 and wasm resolve differently.

**Every escape in this module's triage was closed, and not one of them was a bug in the
port.** `beat-classify.c` took no behavioural edit across the whole triage — its only
edits were explanatory comments, including one *correction* described below. The escapes
split the same way `onset`'s did, into real harness holes and mutants that were equivalent
within the harness's declared contract.

The harness holes, and the cases that closed them:

  - **No case ever turned `enabled` back off.** `enable-midway` switched it on mid-pass and
    nothing switched it off again, so `process()`'s `if (!v->enabled) return 0;` early
    return was only ever observed from the *entry* side. That left three mutants alive at
    once: `enable-reset`, and — because the early return sits above `v->fire_count = 0`
    only in the mutant — `pr-firecount-late`. The producer grew a `disable_at_block` knob
    (the old `maybe_enable` became `maybe_toggle`, applying both directions), and two rows:
    `disable-midway`, which disables on a block that had not just fired, and
    `disable-after-fire`, which disables on block 3 of a dense hat burst at `block_size`
    4096 so the toggle lands immediately after a block that *did* fire. The second row is
    the one `pr-firecount-late` needed — with the first alone the reorder is unobservable,
    because there is no stale `fire_count` to leak.
  - **The stage-2 catch-up clamp never had any work to do.** `if (v->drained <
    det->commit_count - BK_VOICE_PEND_SLOTS)` exists so a voice that has fallen more than
    16 commits behind skips the unrecoverable ones instead of walking them. Every
    `counter_seed` row poked `drained` and `commit_count` to the *same* value, so the
    clamp's condition was false in all 94 rows and `pr-no-catchup` and `pr-catchup-slots`
    both escaped. A `drain_lag` knob now winds `drained` back from the seed, and
    `drain-lag-24`/`drain-lag-24-fast` wind it back **24**, chosen to sit between
    `PEND_SLOTS` (16) and `CAP_SLOTS` (64) so a clamp written against the wrong constant
    is separated from a correct one.

**Three escapes were closed by a proof that the mutant is equivalent, and all three were
replaced rather than written up.** Per the standing rule, no equivalence claim goes into
`beat-classify.c`'s permanent comments unless a replacement mutant the battery
demonstrably catches goes in beside it; the proofs live in the throwaway sweeper.

  - `init-gap-fwd` — deleting `det_opts[MIN_GAP_MS] = defaults[VOICE_MIN_GAP_MS]` writes the
    value already there: `bk_onset_defaults()` ran two lines above, and the detector's own
    min-gap default (45.0, `onset.c`) equals Smart Voice's (45.0, same file as the line
    under test). Any row's own `min_gap` is forwarded again by the `set_param` loop at the
    bottom of `init`. Replaced with **`init-gap-src`** — the right slot fed from the wrong
    default field — which every row that leaves `min_gap` absent now catches.
  - `floor-fwd-clamped` — forwarding the already-clamped `v->floor_db` instead of the raw
    `value` is idempotent, because `onset.c`'s own clamp is *character for character* the
    same bounds, `bk_max(-90.0, bk_min(-6.0, value))`. The comment on the line above is
    still right about the intent — the JS forwards unclamped, and the day either range
    moves the two stop agreeing — but that is a reason to keep the code, not a divergence
    the battery can see. Replaced with **`floor-fwd-drop`**, which deletes the forward and
    leaves the detector on `init`'s floor while the velocity map tracks the row's own.
  - `mtr-level` — reading `v->det.level.env` in place of the cached `v->level` is the same
    load at every point a caller can look. `v->level` has exactly three writers (0.0 in
    `init`, 0.0 in `resetDetector`, `det->level.env` in `process` on the line below
    `bk_onset_process`) and `det.level.env` exactly two (`bk_onset_process`, and
    `bk_env_follower_reset` via `bk_onset_reset`, which `resetDetector` pairs with its own
    0.0 store); `process()`'s disabled early return is above both. Replaced with
    **`mtr-level-stale`**, which swaps those two lines so the cache reads the *previous*
    block's envelope — the staleness a cached field is actually at risk of.

**Two more escapes were equivalent not to the code but to the harness's declared
tolerance, and those are the ones worth reading.** `f1da024` says float32-descended values
are held to `TOL.sampleFloat = 2e-6` rather than to bit-identity. A mutant can therefore
be a genuine behaviour change and still be *inside the contract*, and the right response is
neither to accept it nor to tighten a gate that would then be false.

  - `s1-emit-float-vel` — handing `emit` the float32 out of `pend_vel` instead of the
    unrounded double local. This needs no reachability argument; it is a pure bound. The
    store `v->pend_vel[slot] = (float)vel;` runs two lines above, so the mutant's argument
    is exactly `(double)(float)vel`, and `emit` consumes `vel` twice: `fire_vel[n] =
    (float)vel` is **bit-identical** under the mutant because float→double→float
    round-trips exactly, so the fire record the rack actually plays does not move by one
    bit; and `last_vel = vel`, meter index 4, one of the four tolerance-gated fields. That
    is the only observable difference, and it is the float32 narrowing error of a value
    bounded by 1 — `velocityFrom` returns `vel_min + (1 - vel_min) * c` with `vel_min`
    clamped to `[0, 0.95]` and `c` to `[0, 1]` — hence at most 2⁻²⁴ ≈ 5.96e-8 absolute,
    and `relErr`'s denominator is `max(1, |a|, |b|) = 1`. A factor of 33 under the gate.
    Tightening index 4 to exact equality would be a **false gate**: it descends from a
    float32 IIR through `20*log10()`, which is precisely what `f1da024` declined to hold.
    Replaced with **`s1-emit-vel-floor`**, which emits the velocity *floor* instead of the
    computed velocity and probes the same argument for the right reason.
  - `s1-nan-arm` — writing the raw envelopes instead of exact zeros in stage 1's
    `total > 1e-12` false arm. **This one produced the port's only comment correction.** The
    source claimed the arm was what stops a NaN envelope becoming a NaN feature vector, and
    that is over-claimed: `onset.c`'s per-sample `const double s = isfinite(x) ? (double)x
    : 0.0;` means a non-finite sample never reaches the band filters at all, the biquads
    `bk_sanitize` their own state, and every parameter setter early-returns on `!isfinite`.
    The envelopes are therefore always finite and the NaN leg is unreachable **by
    construction, upstream, in a different file.** That was confirmed empirically rather
    than merely argued: two rows were added at `block_size` 4096 with `n` 32768, which puts
    the poison NaN on the first sample of block 1 while a slot detected in block 0 is read
    by stage 1 *in* block 1 — the tightest alignment the stream allows — and the mutant
    still escaped. Had the envelope been NaN there, `band` would have gone NaN, classify
    would have returned -1, and `emit`'s assert would have aborted the producer loudly. The
    reachable leg is then bounded: entering the arm *requires* each envelope in `[0, 1e-6]`,
    so the mutant perturbs three float32 outputs by at most 1e-6 against a 2e-6 gate, and
    the knock-on through classify shifts squared distances by ~1e-12 — a tie that close
    exists nowhere in the roster. Replaced with **`s1-nan-arm-one`**, a materially different
    write to the same arm, which the rows that reach it now catch outright. The two poison
    rows were kept: they are the evidence for the corrected comment.

Four more replacements came from the earlier passes of the same triage:

  - `s1-axes` — widening stage 1's 3 axes to `FEATURE_COUNT` adds
    `(band[3] - attack[cls*4+3])² * AXIS_WEIGHT[3]`, and both operands are unconditionally
    `+0.0f`: `band[3] = 0.0f` is a straight-line store below both arms of the guard, and
    the attack table's fourth column is `0.0f` for all four classes with its only writer
    rejecting `b > 2` outright — the zcr slot of the attack table is not addressable from
    the API. `d` accumulates only non-negative terms, so `d += 0.0` is bit-exact identity.
    Replaced with **`s1-axes-two`**, a narrowing that drops the high-band axis.
  - `emit-pad-unguarded` — dropping the bounds test in front of `class_pad` cannot be
    anything but an escape in this build: the line above is the `assert`, the battery
    compiles without `NDEBUG`, and the producer is the only caller, so the condition is
    true on every reachable input and false only where the assert aborts both producers
    first. The guard exists for the `NDEBUG` build, where it reproduces what the JS does
    with `classPad[-1]`. Replaced with **`emit-pad-index`**, a permutation of the index that
    the `pad-poke` rows observe.
  - `pr-cap-attack` — capturing the attack vector from `last_band` instead of
    `pend_band[slot]` is equivalent for two independent reasons: a hit closes the previous
    hit's feature window, so at most one slot is pending-unread when the next block's
    stage-1 pass runs; and the drain loop walks ids upward, so a slot read inside the loop
    was registered in the current block and its id exceeds anything the pass read — the
    pass-read slots are captured first, while the pass's write to `last_band` is still the
    newest. Replaced with **two** reachable mutants of the same statement,
    `pr-cap-attack-slot` (wrong pending row) and `pr-cap-attack-order` (right row, reversed).

The 107 mutants are spread across the module by area: `process` 25, `control` 15, `stage1`
13, `reset` 10, `init` 9, `defaults` 8, `classify` 8, `emit` 5, `profile` 4, `capture` 4,
`hazard1` 4, `meters` 2.

**One process note from this module, and it is about tooling rather than DSP.** The triage
ran two instruments: a fast one that patches, builds native only, and byte-diffs the
producer dump against pristine, and the slow one that patches and runs the whole battery.
They answer different questions — the first says *is this mutant reachable*, the second
says *does a check fail* — and a `DIFFERS` from the first was at one point read as "caught",
which is what let `s1-nan-arm` and `s1-emit-float-vel` look closed for a session while they
were in fact reachable-but-inside-tolerance. A reachability probe is not a verdict. The two
were also the only escapes in the module that the fast instrument could not have closed
even in principle, because the hole was in the gate and not in the roster.

Two caveats carry forward unchanged: **MSVC remains completely unmeasured** — the
cross-toolchain agreement here is glibc versus emscripten on Linux/x86-64 only — and
**bit-identity is empirical per module, not a guarantee.** `beat-classify` making the gate
says nothing about `looper` making it.

#### `clock` — the transport, and a NaN that answered the wrong question

`bk_clock` is the transport the looper reads to quantise punches and to keep tempo-locked
loops phase-aligned, which made it the last dependency `looper` needed. It is small (the
JS is a few dozen lines of arithmetic), but it is where tempo turns into frame counts, so
every rounding and every guard in it becomes a looper decision one module later.

**310 records, 57 asserted checks green, 53/53 mutants caught, and all 310
are bit-identical to `clock.js` under both `cc` and `emcc`, and identical between the two
toolchains.** `clock`'s only libm calls are `floor` and `fmod`, and both are exactly
rounded, so unlike `looper` there was no transcendental to drift. The records cover:

  - the constructor at every sample rate the app can meet, plus the degenerate ones;
  - every setter across its clamp boundaries and all three non-finite inputs;
  - the grid sweep, which is every integer bpm from 20 to 300 × 11 quantise choices × 4
    rates;
  - `framesToGrid` anchored to real grid multiples out past 2^52;
  - 600-block `advance` runs with scripted stop, restart and reset;
  - `barPhase` out to 2^53;
  - six scripted sequences that travel as their own params.

**The battery caught two things the first port got wrong. Both were NaN, and neither was
cosmetic.**

  - **`framesToGrid` guarded with `!(g > 0.0)` instead of the JS's literal `g <= 0`.**
    These are not the same test. A NaN grid is reachable: `setParam("bpm", NaN)` makes
    `frames_per_beat` NaN, and the grid with it. The inverted form answers 0, which means
    "act immediately". The JS answers NaN, and in the looper `pendingAt = frame + NaN` is
    a punch that never fires. That is a different decision downstream, not a tidier guard.
    The C now spells the JS's comparison literally.
  - **`beats_per_bar` was an `int` field.** The JS holds a Number, and `clamp()` is a
    ternary that passes NaN straight through, so storing it in an int needed `(int)NaN`.
    That is undefined behaviour in C, and it really does differ between x86 (INT_MIN) and
    wasm (0). The field is now a `double`, like `frame`, for the same reason.

**Three mutants are proven equivalent, and each was replaced on the same line by one the
battery catches:**

  - **`js_round` → `round()`.** `floor(x + 0.5)` and `round()` disagree only on negative
    halves. All three call sites swallow a negative result: `recalc_grid` and
    `frames_for_beats` floor at 1, the `beats_per_bar` setter clamps to [1, 16], and a
    negative half rounds to ≤ 0 either way. Replaced by `nearbyint`, which differs on
    positive halves.
  - **The constructor's grid line → `recalc_grid(c)`.** `bk_clock_init` sets
    `quantize = 4.0` two lines above, so `recalc_grid`'s `quantize > 0` test is statically
    true and the two are the same expression. Replaced by three mutants on the init line
    itself.
  - **`clamp(round(v))` → `round(clamp(v))` for `beats_per_bar`.** Both bounds are integers
    and rounding is monotonic, so the two compose identically for every input including
    NaN and ±Inf. Replaced by the clamp-dropped mutant.

The `param-keys` generator work that `BK_CLOCK_P_*` and `BK_LOOP_P_*` needed was folded
into the same commit.

#### `looper` — the last module, and the one where NaN, `||` and signed zero all mattered

864 lines of C against a 364-line header, a 1522-line script-VM producer and a
1310-line verifier, porting the 925-line `looper.js`. **78 scripted cases,
183 asserted checks green, 250/250 swept mutants caught,** plus 13 more argued
equivalent, each replaced by a caught mutant on the same line. It was the
largest and most stateful module, which is why it went last.

**The battery is a script VM rather than a fixed vector list.** Each case is a flat array
of six-wide ops (record, play, stop, undo, clear, a track or looper param, a clock param,
an advance, a chain insert, process N blocks of M frames from a given source with a given
prefill, and probes for state, snapshot, meters, buffers and queries). The same script
runs through `looper.c` (native and wasm) and through `looper.js`, and every probe is
compared field by field. Scripts are data, so a new edge case costs a few lines and not a
new harness.

**Identity: 77/78 cases are bit-identical to the JS on both toolchains, and
78/78 are identical between native and wasm.** These are pinned as floors, so a
drop fails the run. The one case that is not identical is `init-low`, which runs at 2 kHz.
The play smoother's coefficient there is `exp(-1 / (3 × 0.001 × 2000))`, and V8's
`Math.exp` rounds it one ulp below glibc's (`0.846481724890614` against `…6141`). All 8
differing values are that one `playA` snapshot field (4 tracks × 2 snapshots, 1.1e-16
each). The float32 audio is bit-identical anyway. This is the first module where a libm
transcendental showed up in a record at all, and it is exactly the kind of drift
`f1da024` declined to gate on.

**The port got four things wrong, and the battery caught all of them.** Each one is a place
where a literal C reading of the JS is a different program:

  - **`o.maxSeconds || 30` is a falsiness test, not a default.** 0 and NaN take the default.
    A *negative* value survives the `||`, and then `max(2048, round(neg × sr))` floors it
    at 2048 frames. `js_or_seconds()` spells this out.
  - **`o.tracks || 4` is the same trap.** Only 0 takes the default. A negative count
    survives, and the constructor's loop then builds no tracks at all. The C is
    `tracks == 0 ? 4 : (tracks < 0 ? 0 : tracks)`, and `init` separately refuses anything
    above the 4 the struct holds.
  - **`setParam("source", NaN)` was undefined behaviour.** In the JS,
    `clamp(Math.round(NaN), 0, 1)` is NaN, and `(int)NaN` in C is UB (INT_MIN on x86, 0 on
    wasm). NaN compares unequal to `DRUMS` in the render's only test of the field, so the
    JS behaves as `MASTER`, and the C now stores `MASTER`. The `.mjs` maps a NaN `source`
    to `MASTER` when it snapshots the JS side, and says so.
  - **`bk_clock_frames_to_grid`'s NaN guard is what makes "a punch that never fires"
    reproducible.** With a live grid but a NaN clock frame, `pendingAt = NaN + NaN`, and
    `frame >= NaN` never holds. That fix landed in `clock` (see its section above), but
    `nan-params` is the case that proves the looper consumes it correctly. Its sibling
    proves the other half: a NaN *grid* fails `grid > 0`, so the punch is immediate.

**The always-live buffer argument (looper.h note 1) is proven, not asserted.** The JS
allocates a track buffer on first arm and the undo slot on first overdub. The C has them
from `init`. Three pairs of cases render identically against each other:

  - `arm-never`, `arm-cleared` and `arm-undo` cover buffers;
  - `chain-never`, `chain-empty` and `chain-live` cover the lazy chain (note 2).

Both comparisons are on audio, buffers and snapshots, and the snapshot comparison reports
the differing field.

**Sample-accurate punches are checked across block sizes.** `block-256` and `block-64`
are the same quantised performance at two block sizes. Audio, frame for frame, and the
final snapshot are identical. The final state is identical too, except the meters: they
are the peak of the *last block*, so they depend on block size by design.

**Harness holes the sanity section caught on its own scripts.** Four of the first
`sanity` failures were the battery being wrong, not the port. Each was fixed in the
script, not by loosening the check:

  - `quant-cancel` meant to show a different action *replacing* a pending one. But `PLAY`
    on a playing track schedules STOP, so `STOP, PLAY` was the same action twice, which
    *cancels*. It now uses `STOP, REC`, and checks that the pending action changed while
    `pendingAt` stayed put.
  - In `idle`, `FREE_TAKE` ends with the play gain still at 0, because `begin_take` reset
    it and no block had played since. The following `STOP` had nothing to fade. Four
    blocks are now played first, so the fade is real and is observed as audible, then
    idle 40 blocks later.
  - `BK_CLOCK_P_BEATS_PER_BAR` was never sent by any script.
  - One `nan-params` check read the wrong snapshot index.

gcov then found one real hole: an overdub punched in and out with no frame in between.
`end_overdub` runs with `last_write == -1`, so the declick is skipped. `overdub-instant`
now covers it, and turned up a nice detail along the way. Undo then redo of an empty layer
leaves the loop numerically unchanged but *not* bit-identical, because the redo computes
`-0 + 0 = +0`, and the declick ramp's first sample of a take is a signed zero. That is IEEE
behaviour, the JS does the same, and the check asserts it rather than tolerating it.

**Branches gcov reports as never taken, and why each one is unreachable:**

  - **Every NULL-buffer guard** (`!t->buf_l`, `!lp->undo_l`, `&& buf_l` in the render, and
    their kin). Buffers are always live (note 1).
  - **`bk_chain_init` failing inside `init`.** Its four refusals (NULL chain, NULL wet,
    `max_block <= 0`, too many slots) are pre-checked by `init` itself or constant, so
    with `init` intact the branch cannot be taken. It is not dead weight, though: it is a
    second line behind `init`'s own checks. That is exactly why two first-sweep mutants
    (`init: max_block <= 0 -> < 0` and `init: chain_wet_r unchecked`) were equivalent.
    Loosen one of `init`'s checks and the chain refuses the same input, so `init` still
    returns -1. Both were replaced (see below).
  - **`value > 1e-4` in `audible`, and the matching `<= 1e-4` in the idle test.** A track
    that is not playing always has `play_gain.target == 0`. Every transition to
    EMPTY/REC/STOPPED sets or resets the target to 0, the undo-take redo inherits the 0 the
    undo set (or that `begin_take` reset, if a new take was started in between), and a non-playing track that renders gets `want_gain` 0. "Settled" means
    `value == target`, so settled and not playing implies a value of exactly 0.
  - **`undo_mode == NONE` while `undo_track` names the track.** `undo_track == -1` holds
    exactly when the mode is `NONE`: the only writers are `init`/`drop_undo` (both) and
    `close_take`/`begin_overdub` (both).
  - **`n <= 0` in the layer undo.** In LAYER mode, `frames > 0` holds from `begin_overdub`
    until `clear`, which drops the undo. `undo_frames = min(frames, max_frames) > 0`.
  - **`undo_mode != LAYER` while `undo_armed`.** `armed` is only set alongside LAYER, and
    is cleared by every path that changes the mode.
  - **`idx < 0` in the REC declick.** `n <= rec_write`, so `idx = rec_write - 1 - k >= 0`.
  - **The free-running `pos >= len` wrap at read time.** `t->pos ∈ [0, frames)` whenever
    `frames > 0`. It is set to 0, wrapped by `%`, or advanced with a wrap. The one place
    `frames` is restored (undo-take redo) restores the same length the position was valid
    for.
  - **`begin_play`/`begin_overdub` with `frames <= 0`, and `action != STOP` in the last arm
    of `apply_action`.** Both are excluded by their only callers.

Writing this section turned up two of my own equivalence arguments that were wrong:

    deliberately ported without a JS-parity gate, and reading it is what forced the

    never touches the audio thread — it runs at kit-build time and when a knob moves in
    the kit editor, rendering up to 4 seconds into a buffer in one call. That is what
    "offline" means here: off the audio thread, in both builds, not "the exe only". It is
    also the only module so far where sample-level agreement with V8 is **not achievable
    at any tolerance worth asserting**, for two structural reasons:

      - **Peak normalisation is global.** `renderDrum` scans the finished render for its
        peak, then scales every sample by `0.89 / peak`. One ULP of divergence that lands
        on the peak sample changes the gain applied to the *entire* buffer. A local
        difference becomes a global one.
      - **The hat renderer puts a comparator on a transcendental**: `m += Math.sin(ph[k])
        >= 0 ? 1 : -1`, six inharmonic partials summed as square waves. One ULP in `sin`
        near a zero crossing doesn't shift a sample slightly, it flips ±1 — a ~30%
        instantaneous step. Across ~260k comparisons in a 900 ms ride, near-crossings are
        a certainty, not a risk.

    So its battery is built on **self-consistency and behaviour** instead: the same build
    renders the same kit byte-for-byte against its own pinned baseline (which still
    catches every real regression), each of the six kinds lands in its expected band on
    peak / RMS envelope / decay length / spectral centroid, no NaN and no clipping
    survives `sanitize`, the 2 ms fade-out actually reaches zero, the xorshift noise is
    deterministic per seed, and all 16 `DEFAULT_KIT_LAYOUT` entries render. Mutation
    tested like everything else. `cc`-vs-`emcc` divergence gets measured and recorded
    because it costs nothing and makes a useful canary — it just isn't a gate.

    **Watch for the libm constant-folding trap here specifically:** LLVM folds `cos`/
    `sin`/`pow` on literal arguments using the *host's* libm at compile time, which makes
    `cc` and `emcc` appear to agree when they don't. Any micro-benchmark comparing the two
    must take its input through a `volatile`. This module is full of exactly those calls.
  - Each module gets its own parity battery, and each battery is itself mutation-tested
    before it is believed. Shared plumbing lives in `packages/native/tests/parity-io.h`
    (binary stream format v3, plus the deterministic stimulus generator) and
    `scripts/lib/parity-stream.mjs` (the JS-side reader and comparators), so a new module
    costs a battery and a runner, not a new harness.
  - **JS parity is a porting aid, not a gate — decided 2026-09-15, and it narrows the
    remaining work.** The original framing had C canonical for *both* targets, which made
    "the wasm and the `.js` agree" a shipping requirement and put a bit-identity baseline

    the web build is a demo, and Ableton doesn't have a browser version either. So from

### Risks, stated plainly

1. **This is the least certain phase in the plan.** Phases 1–3 were engineering; Phase 4
   was research with a known shape. This is systems work against hardware I cannot see,
   and the blind-iteration loop on 5b is real.
2. **WASM-in-a-realtime-callback is the load-bearing bet.** If it can't be made to run

### 6b — MIDI: rescan, and telling you the truth about why a port is missing

**I don't think a rescanner is the real fix, and I want to be straight about why.** Windows'
WinMM MIDI driver model is **single-client**: the first application to open a port owns it
exclusively. Ableton is open and holding your ports, so Chromium *cannot* open them — no
amount of rescanning changes that. Your UMC1820 has DIN MIDI I/O built in, which is very
likely one of the ports in question.

What's genuinely wrong on our side, in `audio/midi.ts`:

- **No manual rescan.** We only refresh on `access.onstatechange`, which doesn't fire for
  a port that was already unavailable when we asked.
- **We never call `port.open()`.** We attach `onmidimessage` and assume the port is live.
  A port that fails to open is indistinguishable from one that doesn't exist.
- **No per-port error state.** `MidiInputInfo` carries `connected` but no reason, so a
  held port renders as absent.

The fix: an explicit **RESCAN** button that re-runs `requestMIDIAccess` and `open()`s every
port individually, recording per-port success; a port list that shows `HELD BY ANOTHER APP`
or `FAILED TO OPEN` with the error, not silence; and a plain-English note naming the
single-client limitation and the two real workarounds (close the other DAW, or a
multi-client virtual port like loopMIDI). **The actual solution is Phase 5's native addon
using WinRT MIDI, which is multi-client** — worth sequencing if MIDI matters more than
latency.

### 6c — The scope's dead right half: found, fixed, and it was our bug

You said the VU pair is fine and **the right side of the scope doesn't move**. That was
exact, and it was a real defect in our code — not your interface. Fixed already:

`EngineClient.scope.input/output` are `Float32Array(2048)`, deliberately over-allocated so
any window size can be requested without reallocating. Both drawing paths ask for
**1024** frames, so samples 1024–2047 were **never written and stayed zero for the life of
the session**. But both paths then took their sample count from `buf.length` — 2048 — so
every pixel past the halfway mark indexed that dead memory and drew a flat line pinned to
the centre graticule. Live left half, frozen right half, exactly as you described. It hit
the oscilloscope *and* the small wave strip in the meters pane.

The fix, now in:

- **`ScopeFrame` carries `frames`** — how many leading samples the last read actually
  filled. `pollScope` sets it; both consumers read it instead of `buf.length`. The
  interface now documents why, so the next consumer can't repeat it.
- **A fixed time base.** The sweep used `span = n - trig`, so the horizontal scale changed
  every frame as the trigger moved: the trace stretched and breathed to the right of the
  trigger point even on a steady tone. The span is now constant (half the window) with a
  variable start — how a bench scope actually works.
- **Proven in `scripts/verify-scope-window.mjs`**: reproduces the old behaviour (≈half the
  canvas width reading dead memory), then asserts that at *every* trigger offset the new
  sweep touches only live samples and keeps a constant scale. Passes.

Separately, and still worth doing — the thing I originally mis-diagnosed this as. The
UMC1820's Windows driver exposes **four stereo-pair devices** (Line 1&2, Line 3&4, …) and
all eighteen inputs are mono, hard-panned: input 1 is the left of "Line 1&2", input 2 its
right. With one mic in input 1 and nothing in input 2, the right channel is **genuinely
silent** — we ask for `channelCount: 2` and get `[mic, silence]`. That is correct
behaviour displayed without explanation, and it also costs you 6 dB the moment anything
folds to mono. So:

- **An input channel selector** in the I/O strip: `STEREO` / `LEFT` / `RIGHT` / `SUM`.
  Your mic is on **input 2**, which on this interface is the **right** leg of its stereo
  pair — so the correct default for your rig is `RIGHT`, not `LEFT`, and the silent leg
  you were staring at is channel 1. The selected channel feeds both legs. The engine's
  mono fold already does the maths, but it *averages*, which costs a one-sided mic 6 dB —
  so `LEFT`/`RIGHT` copy instead of averaging and keep the level.
- **Dead-channel detection.** If one channel stays below ~-70 dBFS for several seconds
  while the other is active, the device panel says so and offers the one-click fix, rather
  than leaving a dead needle to interpret.
- **Name the pair in the device list.** Chromium reports these as generic names; showing
  which stereo pair is selected makes the 4-device layout legible.
- Verified in `scripts/verify-input-route.mjs`: each mode's channel mapping, the level
  preservation on `LEFT`/`RIGHT` vs `SUM`, and the detector firing on a synthetic
  one-sided input.

### 6d — Visualiser polish: the existing panes, sexier, no WebGL

**Dropped 2026-10-01, your call:** the WebGL pane, its three 3D styles and the style dial.
That also removes 6d's main risk: a GPU context competing with the audio callback, plus
the fallback path that existed to manage it. What stays is the two panes that already
work:

  - `ScopeStrip` "vu": the two analogue VUs either side of the triggered oscilloscope;
  - `SpectrumStrip` "spectrum": waveform over a log-frequency spectrum.

Both are canvas 2D, and both get a look pass. **No new DSP and no change to the SAB
layout.** Everything below draws from the `pollScope` and `readSpectrum` data that already
exists.

  - **Phosphor persistence on the scope.** The trace is drawn into an offscreen canvas
    that is faded by a fraction each frame instead of being cleared. Steady signals burn
    in bright and transients leave a decaying tail, which is what a real CRT does. Add a
    soft glow: one wide, low-alpha stroke under the sharp one, and **not** `shadowBlur`,
    which is the expensive canvas-2D path.
  - **A proper CRT glass.** A vignette, faint scanlines and a cached graticule, rendered
    once per resize rather than per frame. A per-division scale readout goes in the corner
    (`0.25 / div`, and `ms / div` from the sample rate).
  - **The spectrum gets its reference numbers.** This was the real ask behind the old 6d.
    Frequency labels move from three lines to the full decade set (20, 50, 100, 200, 500,
    1k, 2k, 5k, 10k, 20k). A labelled dBFS axis goes up the side. A hover crosshair reads
    out the frequency and level under the cursor, for hunting a resonance.
  - **Spectrum fill as a gradient.** The fill runs from the band colour at the trace down
    to transparent, with a peak-hold trace that has real hold-then-fall ballistics. Today
    it is a constant 0.6 dB a frame.
  - **Optional, your call: a 2D goniometer** (L against R) as a third mode. It is
    cheap in canvas 2D at 1024 points, and it is the one useful idea in the old Lissajous
    style: a mono-on-one-channel signal draws a line, not a field. The catch is that it
    needs the scope ring widened to stereo. Today the worklet sums `(inL+inR)*0.5` into one
    ring. That change is additive to the SAB layout, but it is a DSP-side change, so it is
    listed separately.

**Frame budget:** 30 fps when the CPU meter climbs, and drawing suspended when the pane is
not visible. That rule carries over from the old 6d unchanged, because canvas 2D on the
main thread can still starve the UI if it is careless.

### 6e — Harmonizer: an H3000-style pitch shifter in the chain

**Spec (from your answers):** "just like the Eventide H3000". That means up to 4 harmony
voices, user-configurable, real-time with low latency for live vocal monitoring. If
bit-identity breaks, we decide then.

**The approach is decided by the latency, not by taste.** A phase vocoder (what the
existing `PitchFormant` uses, at FFT 1024) sounds cleaner but needs a long analysis
window, and the window *is* the latency. The H3000 reached roughly 10 ms with
**time-domain splicing**: two read heads crossfading through a short delay line, with the
splice points chosen to land on matching waveform phase. The artefacts of that approach
are what people now call "the H3000 sound". So copying the approach is both the only
low-latency route and the way to get the character.

**What it is, built in two stages so the risky part is heard early:**

  - **Stage 1: one fixed-interval voice, end to end.** A splice shifter (±24 semitones plus
    fine cents) on the existing `delay-line` core, with correlation-picked splice points.
    It covers the params, the chain slot, the worklet and a UI card. The point of this
    stage is that you hear the shifter's quality before anything is built on top of it.
  - **Stage 2: the H3000 layer.**
    - Up to 4 voices, each with its own interval, level, pan, delay (0–2 s) and a damping
      low-pass.
    - A feedback path per voice, which gives the cascading arpeggio effect.
    - A **diatonic mode**: a pitch detector plus a key and scale picker, so each voice
      shifts by a scale degree rather than a fixed number of semitones.
    - Factory presets.
    - The pitch detector should start from the vocoder's autocorrelation tracker (its
      `PITCH FOLLOW`), not from scratch.

**Under route (c) it is written in C first.** There is no JS reference. By Phase 6, the 22
effects and the engine are in C and the demo runs the wasm build. Writing a JavaScript
version first only to port it would be throwaway work. That changes what the battery can
assert. There is no V8 oracle, so it is behavioural:

  - pitch accuracy on known sines and sawtooths at every interval;
  - **measured latency**, asserted under a ceiling;
  - voice count and level;
  - feedback that decays and never runs away;
  - splice clicks below a set threshold;
  - no NaN and no denormal stall;
  - the same output at every block size;
  - native against wasm across toolchains.

The battery is mutation-tested like everything else.

**Scope: about 13–23 sessions**, against roughly 4 for `drum-rack`. This is the earlier
15–26 estimate less the C-port line, since there is now no JS to port from.

  - Stage 1 is about 5–7 sessions.
  - Stage 2 is about 8–16 sessions.
  - **Two risks dominate.**
    - **The pitch detector on real vocals.** This is the hardest DSP in the app, and it is
      judged by ear.
    - **Splice tuning.** Making it sound like an H3000 rather than a broken granular
      stretch is ear work, and no test says when it is done.

  Quote it in two stages: Stage 2 gets a real estimate once Stage 1 has been heard.
